# Moderator Playbook — подготовительный проект EGO-105

Статус: **DRAFT / НЕ ДЕЙСТВУЮЩИЙ РЕГЛАМЕНТ**, 01.11.2026.
[Карта категорий](../product/ugc-safety-policy-proposal.md) и
[реестр решений владельца](moderation-owner-decisions.md) читаются вместе с этим
документом. Кнопки/API будущего post-publication процесса пока отсутствуют.

## Дерево решения для существующей pre-publication очереди

1. Убедиться, что используется персональный авторизованный moderator/admin actor
   с актуальной ролью в БД. Обычный пользователь, creator, support и finance не
   получают права модерации через эту инструкцию. При denied доступе не выдавать
   себе роль и не использовать чужой аккаунт.
2. Открыть pending item из существующей очереди. Проверять точный приватный
   cleaned Asset, связанный с owner approval. Не скачивать оригинал и не
   переносить signed URL, изображение или личные сведения в чат, issue, скриншот
   отчёта или общие журналы. При истечении preview использовать его штатное
   обновление, не делать bucket публичным.
3. Проверить непосредственную угрозу, сексуальную эксплуатацию несовершеннолетних
   и doxxing. При таком риске прекратить распространение evidence и передать
   минимальный внутренний идентификатор дежурной уполномоченной роли по заранее
   принятому плану. Для явно запрещённого pending материала применима обычная
   rejection; она не реализует срочное снятие уже публичного материала.
4. Последовательно проверить сексуальный контент; угрозы/насилие; ненависть;
   персональные данные; deception; права/остальные ограничения; пригодность
   декоративного объекта. Учитывать контекст, а не только символ или dislike.
5. Если нарушение ясно, выбрать один точный существующий reason code и reject.
   Если контент допустим, approve. Если фактов недостаточно, не придумывать
   юридический вывод и не approve ради опустошения очереди: оставить pending и
   передать специалисту. Отдельной кнопки escalation/hold сейчас нет; такое
   обращение возможно лишь через заранее проверенный закрытый процесс.
6. На сетевой ошибке проверить итог и безопасно повторить то же решение.
   Противоположное решение при MODERATION_ALREADY_DECIDED не «чинить» SQL:
   evidence неизменяем. Backend повторно проверяет роль, статус и совпадение
   текущего immutable owner approval/cleaned evidence, сериализуя решение на
   Autograph. Нынешний decision API не принимает expected-version или
   client-reviewedAssetId; expected-version ниже относится к будущему EGO-134.
7. Проверить итоговый статус. ready разрешает дальнейшее consideration для
   Placement, но не подтверждает личность и не означает публикацию или продажу.

Сейчас запись решения содержит actor, server time, approval, cleaned asset,
decision и reason code, но не freeform notes или policy-version FK. Не
притворяться, что существующий UI сохраняет произвольное rationale. Для
будущих cases нужны ограниченные закрытые policy references и audit согласно
архитектуре EGO-134; их нельзя собирать в общедоступных комментариях.

## Срочная эскалация и эксплуатационные пределы

Триггеры: конкретная непосредственная угроза; возможная сексуальная эксплуатация
ребёнка; раскрытие credentials/адреса/чувствительных сведений; иная ясно
высокорисковая ситуация. Код категории не является автоматической urgency.
Не воспроизводить незаконный материал для «проверки», не пересылать его и не
проводить собственное расследование личности.

До пилота должны существовать назначенный on-call owner и backup, проверенный
закрытый канал, подтверждение получения, разрешённое временное ограничение
публичной доставки, legal/privacy escalation и процедура при недоступном
дежурном. Сейчас этот пакет их не создаёт. Если безопасное реагирование не
подтверждено, открытый UGC pilot остаётся заблокирован.

Канонический draft §§13–15 содержит контакт и отдельные правовые сроки. Это
provenance для владельца/юриста, а не подтверждение работающего mailbox или
утверждённый общий SLA. Не направлять тестовые письма и не включать доставку
по этому пакету. Юридические сроки нельзя заменять будущими внутренними SLA.

## Будущий post-publication процесс — только проект

1. Authenticated reporter сообщает точный доступный Placement; сервер фиксирует
   actor-bound idempotent receipt и минимальные evidence references. Жалоба не
   даёт доступа к чужим приватным данным. Несуществующий сейчас report UI нельзя
   обещать пользователю.
2. Уполномоченный reviewer проверяет факты и конфликт интересов. Только после
   отдельной реализации overlay допускаются temporary hide/remove/dismiss;
   решение и audit коммитятся вместе с expected-version проверкой.
3. Hide не освобождает Slot и не меняет деньги. Все public Wall/media/share/history
   и будущие admission пути применяют один overlay. Уже скопированные публичные
   байты невозможно обещать отозвать из чужого кэша.
4. Owner appeal относится к точному decisionId. Reviewer пересмотра сохраняет
   новое evidence, не меняет первоначальную запись, проверяет privacy/deletion и
   все другие active holds до restore. Creator не апеллирует от чужого имени.
5. Сроки, допустимость повторов, уведомление сторон и право на независимого
   reviewer утверждаются в реестре решений. Ошибку не учитывать как strike.
   Автоматические refund/suspend/ban не являются шагом этого процесса.

## Офлайн-калибровка для двух модераторов

Использовать только безопасные словесные карточки ниже, без реального запрещённого
контента, контактов и подписанных URL. Модераторы сначала независимо записывают
allow/reject/escalate, code (если reject), срочность и краткое объяснение в
разрешённом закрытом протоколе репетиции. До согласования privacy процесса
не собирать реальные пользовательские evidence.

Ключ ниже — ожидаемая интерпретация проекта, не запись фактически проведённых
интервью или согласие модераторов. При нескольких нарушениях допустим иной
конкретный code, если это мотивировано и затем единообразно согласовано.
ESCalate означает организационную передачу, не реализованное состояние БД.

- C01. Читаемая абстрактная звезда и вымышленный псевдоним. Ожидание: allow;
  нет признаков нарушения, авторство личности не удостоверяется.
- C02. Обычная фанатская надпись без чужих данных или endorsement. Allow.
- C03. Непустой, но бессмысленный повреждённый объект. Reject NOT_AN_AUTOGRAPH;
  никакого strike за техническое качество.
- C04. Художественная нагота без сексуального действия. Reject SEXUAL_CONTENT
  по текущему draft §3; не подменять его более мягким личным стандартом.
- C05. Словесная карточка о возможной сексуальной эксплуатации ребёнка.
  Срочная escalation; явно запрещённое pending содержимое reject SEXUAL_CONTENT.
  Не создавать или разыскивать иллюстрацию для упражнения.
- C06. Конкретная непосредственная угроза человеку. Reject THREATS_OR_VIOLENCE
  и срочная escalation; не обещать, что одно отклонение решает реальную угрозу.
- C07. Спокойная надпись о восстановлении после тяжёлого периода без инструкций.
  Allow при отсутствии иных нарушений; тема самоповреждения сама по себе не ban.
- C08. Призыв или инструкция самоповреждения. Reject THREATS_OR_VIOLENCE;
  срочность оценивается по фактам, а не автоматически по code.
- C09. Образовательный контекст исторического символа, смысл которого неясен.
  Escalate для контекстной оценки; символ сам по себе не юридический вердикт.
- C10. Явный призыв к насилию против защищённой группы. Reject HATE_OR_EXTREMISM.
- C11. Частный адрес или credentials, включая заявленные как собственные.
  Reject PERSONAL_DATA; высокорисковая утечка требует срочной escalation.
- C12. Имитация официальной подписи артиста с ложным endorsement.
  Reject IMPERSONATION_OR_DECEPTIVE; модератор не проводит экспертизу почерка.
- C13. Сатирическая критика creator без угроз и чужих данных; creator недоволен.
  Allow при отсутствии других нарушений; просьба creator не является решением.
- C14. QR или внешний URL на внешне безобидный сайт. Reject
  OTHER_POLICY_VIOLATION по ограничению MVP; не называть сайт незаконным и не
  переходить по ссылке с модераторского рабочего места.
- C15. Известный логотип с неясной лицензией/контекстом. Escalate на проверку
  основания; не reject автоматически лишь за узнаваемость.
- C16. Подтверждённое нарушение прав после проверки контекста. Reject
  ILLEGAL_OR_PROHIBITED с закрытой ссылкой на основание по будущему процессу;
  текущий API сохраняет только code.
- C17. Политическая агитация/сбор средств, запрещённые draft §9. Reject
  OTHER_POLICY_VIOLATION; обычное мнение отдельно не приравнивать к агитации.
- C18. Обманная синтетика, изображающая ложное одобрение конкретным человеком.
  Reject IMPERSONATION_OR_DECEPTIVE; происхождение AI само по себе не причина.

### Сценарии будущего workflow и контроля доступа

Для C19–C22 записываются ожидаемый control/outcome и затрагиваемая граница,
а не allow/reject/code. Их согласованность считается отдельно от решений по
контенту; они не подтверждают реализацию будущего API.

- C19. Уже оплаченный объект с подтверждённым нарушением. Escalate в будущий
  post-publication процесс; оплаченный статус не исключение, refund не автоматичен.
  Текущий pre-publication API уже финального объекта не переоткрывает.
- C20. Сто одинаковых жалоб без новых фактов. Review по существу; не auto-hide,
  не auto-ban и не раскрывать репортёрам case counts/личности других.
- C21. Appeal на ошибочное hide при другом активном privacy hold. Будущий review
  сохраняет отмену ошибки, но не restore через оставшийся hold.
- C22. Отозванная роль и открытая ранее вкладка. Любое новое действие denied
  сервером; не использовать cached UI authority.

### Дополнительная карточка категории

- C23. Пользователь явно описал изображение как свой настоящий банковский
  образец подписи или паспортный образец. Reject PERSONAL_DATA по §2 и safety
  ограничению, несмотря на заявление о собственном авторстве. Не запрашивать
  настоящий документ для проверки и не использовать его в упражнении.
- C24. Серьёзное персональное обвинение, которое обычный moderator не может
  безопасно проверить. Escalate для specialist/context review по §6, без
  самостоятельного юридического вывода; отличать от обычной критики C13.

Форма результата репетиции: case ID; анонимный код reviewer; независимый выбор;
code/urgency; совпадение по действию и категории; причина расхождения; решение
арбитра; версия проекта. Считать долю совпадений отдельно по действиям и codes,
показывая denominator и нерешённые urgent cases. Для C01–C18/C23–C24 считать решения
по контенту; для C19–C22 — согласованность workflow/access outcomes отдельно.
Целевой порог, критерий повторной
репетиции и арбитра утверждает владелец; здесь не заявляется PASS.
