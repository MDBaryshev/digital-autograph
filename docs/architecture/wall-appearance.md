# Wall appearance

An owner can submit a Wall title (100 characters), description (500), avatar and cover in account settings. The Wall uses the approved appearance. Empty text retains the creator-name fallback. A removal of the owner's avatar or cover takes effect on save. The authenticated submission is Origin-checked, first-use guarded and subject to `CREATOR_PROFILE_PUBLICATION_APPROVED`, which is closed by default. [Profile moderation architecture](account-content-moderation.md#ручная-проверка-профилей)

Migration 0026 adds `account_appearance`: one bounded row per account, with three JPEG derivatives at most 350,000 encoded characters each (published avatar, cover, private provider candidate). PostgreSQL constraints bound each field and preserve the explicit avatar-source selection. API-only SELECT/INSERT/UPDATE grants are added; the worker has no access. Manifest validation accepts the 27-migration release and still requires exact receipts/hashes. Originals are never persisted by this feature. These profile derivatives are separate from original autograph assets and their moderation/ownership evidence.

The browser crops a selected PNG/JPEG/WebP (at most 10 MB / 20 megapixels) to a small preview. The server independently validates canonical base64, byte signature, MIME and decoder format, rejects animation and unsupported formats, limits decoding to four megapixels and 256 KiB input and strips metadata. It produces JPEG derivatives up to 256 KiB each, with a 256×256 avatar and a 1200×400 cover. Two decoders may run at once. The public Wall receives only approved derivatives and text. PostgreSQL stores these derivatives and the private moderation submissions. Account export, deletion and backup retention must cover both tables (EGO-110).

After verified OAuth identity and successful session creation, an optional photo claim can be imported as a **private candidate**. Failure or absent photo never fails sign-in. An import never changes the saved avatar. The owner can select the candidate, upload a replacement, or retain initials. This choice persists across reloads; a later text-only save cannot restore a removed photo.

Only known provider-controlled HTTPS image hosts are fetched, with no credentials, custom port or redirects; a five-second deadline and 256 KiB stream limit apply. The image is normalized before persistence. External image URLs never reach the public page or its visitors. Google and Telegram request the optional `profile` scope only when profile publication/import is enabled. Yandex additionally requests `login:avatar`; VK uses the existing `vkid.personal_info` contract and only exposes the verified optional photo when enabled. No email/phone scope or identity linking rule changes.

Provider references: [Google OpenID claims](https://developers.google.com/identity/openid-connect/openid-connect), [Telegram OIDC scopes](https://core.telegram.org/bots/telegram-login), [Yandex portrait permission](https://yandex.com/dev/id/doc/ru/user-information), [VK ID SDK user information](https://vkcom.github.io/vkid-web-sdk/docs/interfaces/auth.UserInfoResult.html). Provider-side settings and consent still determine whether a photo is supplied. No live user-account import or production activation is claimed by synthetic tests.
